# 合成 pilot：用 persona 代理在真实应用里试用

> Hao 2026-10-20 提出：设计一个代理，开新账号、像 pilot 用户一样用应用，用不同口味的 persona
> 产生测试数据，再从可观测数据和指标里找问题，在交给真人之前修掉。

## 1. 问题 / Problem

真人 pilot 还没开始，而我们对三件事心里没底：

1. **真实流程里还有多少缺陷。** 历史上最贵的两次事故（池子没接进摇一摇、自动刷新零调用点）
   都是单元测试全绿、但真实流程断了。只有「像用户一样从头用到尾」才抓得到这类问题。
2. **「越用越懂你」在真实应用里成不成立。** research/0002 在离线模拟里证明了引擎能学，
   但那是 Python 版、理想化的输入。真实应用里经过 UI、存储、云端同步之后还成不成立，没人验证过。
3. **出了问题我们看不看得见。** Supabase 里有 `admin_*_feed` 视图，但从没被拿来回答过一个
   具体问题。pilot 开始后才发现「想看的数据没记」就晚了。

## 2. 目标与非目标 / Goals & Non-goals

**目标**
- 在真实生产环境（真实 UI、真实 Supabase）里跑完整的用户旅程，产出**缺陷清单**。
- 对每个 persona，回答「**引擎在第几天开始摇出他喜欢的店**」，并与 research/0002 的离线结论对照。
- 用产生的数据实际回答一组运营问题，暴露**可观测性的缺口**。

**非目标**
- **不是压力测试。** 3–4 个 persona，量级就是 pilot 的量级。
- **不把 LLM 的「口味」当成用户真相。** 代理说「这家店不错」不代表任何用户会这么想；
  学习效果只拿**脚本里写死的真实偏好**来度量。
- **不替代 `sim/sim.py`。** 离线模拟回答「算法对不对」，本文回答「产品通不通」。

## 3. 成功长什么样 / Success criteria

- 每个 persona 跑满 30 个模拟日，数据完整进库，并且能和真人数据**一条 SQL 分开**。
- 一份 research 报告：缺陷清单（分级）、每个 persona 的学习曲线、可观测性缺口、跟进清单。
- 整个过程 Places / DeepSeek 的额外调用 **≤ 50 次**（见 §6 的配额风险）。

## 4. 方案 / Proposed design

### 4.1 两种代理，各干各的

Hao 的设想是「一个代理开账号、用应用」。创始人建议拆成两种，因为要的两样东西性质不同：

| | A. 探索型测试员 | B. 数据型 persona 驱动器 |
| - | --------------- | ----------------------- |
| 是什么 | Sonnet 子代理，通过 Playwright 像人一样点 | 一个 Node 脚本，通过 Playwright 按固定规则点，**每一步不调 LLM** |
| 找什么 | 缺陷、卡壳、看不懂的文案、视觉问题 | 学习曲线、数据完整性、指标 |
| 量 | 每个 persona 1 次完整会话 | 每个 persona 30 个模拟日，每天 1–3 摇 |
| 为什么这样 | 找「没想到的问题」需要判断力 | 量学习效果需要**已知的真实偏好**，还要可复现；每一步都调 LLM 既贵又不可复现 |

### 4.2 Persona（初稿，等 Hao 改）

| persona | 界面语言 | 真实偏好（脚本里写死） | 要压到的功能 |
| ------- | -------- | ---------------------- | ------------ |
| 🌶 重口川湘 | 中文 | 川湘、火锅、串串高；粤菜、西餐低；能接受 8 km | 套餐「精选中餐」、按「不想吃这个菜系」跳过 |
| 🍝 约会西餐 | 中文 | 西餐、日料高；快餐低；价位高无所谓；周末才出远门 | 套餐「高性价比西餐」、按「太远」跳过、补问反馈 |
| 🍜 一人食打工人 | 中文 | 面、米线、粥粉面高；3 km 以内；不要贵的 | 套餐「一人食快手」、GPS 半径、按「太贵」跳过 |
| 🌏 英文界面新邻居 | **English** | 东南亚、日韩高；中餐中性 | 语言切换、英文文案、粘贴笔记导入 1 家店 |

### 4.3 代理 B 怎么模拟 30 天

- 用 Playwright 的 `page.clock` 把浏览器时间拨到第 *n* 天 18:30，执行当天的动作。
  应用写进库的 `rolls.rolled_at` / `epoch_day` 都来自客户端时间，所以模拟日会如实落库；
  服务端的 `created_at` 仍是真实时间，因此也能分辨出这些数据是哪天灌进来的。
- 每天：打开 → 摇 → 按 persona 的真实偏好算接受概率，掷骰子决定接受或跳过（跳过时选与原因相符的
  skip reason）→ 第二天打开时回答补问（好 / 一般 / 差，同样按偏好）。随机种子固定，可复现。
- **拦截 `/api/refresh/*` 与 `/api/explore/*`**（Playwright route）：否则每个模拟日都会触发一次
  自动刷新，30 天 × 4 个 persona 最多会打出上千次 Places Details。代理 A 不拦截，
  但每个 persona 最多导入 1 家店。

### 4.4 账号与数据隔离

- 账号统一用 `pilot+<persona>@supper-valet.local`（与现有的 `test+N@` 区分开），口令写进
  `app/web/.env.local`，不进仓库。
- **所有分析都按邮箱前缀把 pilot 数据分开。** 新增一个只读视图 `admin_cohort`（加视图，属于
  可自主的迁移），把 `user_id` 标成 `pilot` / `test` / `real`，以后任何指标都先按它分组。
  否则 pilot 开始后的第一份「真实用户」数据，会被这几百条合成数据污染。
- 跑完**不自动删除**。删账号会级联删数据，属于「删除已有数据」，要 Hao 当次批准。

### 4.5 产出：一份报告，回答一组具体问题

写成 `docs/research/NNNN-synthetic-pilot.md`，每个问题都附上回答它的 SQL：

1. 每个 persona，第几天起「接受率」稳定超过 50%？与 research/0002 的离线曲线对比。
2. 从 `candidates_snapshot` 里看两层 θ：引擎学到的菜系排序，和 persona 的真实偏好排序的一致程度（Spearman）。
3. 跳过原因的分布，和 persona 的设定是否一致（检验按跳过原因的学习有没有生效）。
4. 30 天里摇到过多少家**不同的**店（多样性；检验「几何坍缩」有没有复发）。
5. 补问的回收率与延迟。
6. **哪些问题我们回答不了**，因为数据没记 —— 这一条就是可观测性的跟进清单。
7. 代理 A 的缺陷清单：阻塞 / 严重 / 一般 / 建议，附截图。

## 5. 备选方案 / Alternatives considered

| 方案 | 优点 | 缺点 | 为什么没选 |
| ---- | ---- | ---- | ---------- |
| **两种代理分工**（本方案） | 判断力花在找缺陷上；学习效果用已知真相度量，可复现 | 要写一个驱动脚本 | — |
| 只用 LLM 代理，让它连续用 30 天 | 最像真人 | 每一步都调模型，贵且不可复现；它的「口味」不是可度量的真相；30 天要么真等 30 天，要么还是得拨时钟 | 量不出学习效果 |
| 只用脚本 | 便宜、可复现 | 脚本只会按我们想到的路径走，正是抓不到「没想到的问题」 | 漏掉最值钱的那类缺陷 |
| 直接写库，伪造 rolls / feedbacks | 最快 | 绕过了 UI 和存储层 —— 恰恰是历史事故发生的地方 | 测不到要测的东西 |
| 在单独的 Supabase 项目里跑 | 完全不污染生产 | 免费档只给 2 个项目；测的就不是生产了 | 用视图隔离代替 |

## 6. 风险与未决问题 / Risks & open questions

- **Risk: 配额。** 自动刷新每个模拟日都会触发。**缓解:** 代理 B 拦截 `/api/refresh/*`；
  报告里记一行实际调用了多少次。
- **Risk: 合成数据混进真实数据。** **缓解:** §4.4 的 `admin_cohort` 视图，以及固定的邮箱前缀。
- **Risk: `page.clock` 与应用里的某些计时器不兼容**（如动效、15 分钟的 GPS 缓存）。
  **缓解:** 先跑 1 个 persona 的 3 个模拟日做冒烟，再放开。
- **Risk: 测到的是被拨过时钟的应用，不是真实时间里的应用。** 这一点接受：代理 A 用真实时间跑一次，补上这个缺口。
- **Open:** persona 的具体偏好与人数，等 Hao 改。
- **Open:** 跑完之后 pilot 账号留着还是删掉（删要 Hao 批准）。

## 7. 落地计划 / Rollout

1. `admin_cohort` 视图（迁移 0007，加视图）。
2. 代理 B 的驱动脚本 `scripts/pilot/`（Playwright 只装在这个目录，不进 `app/web` 的依赖），
   先用 1 个 persona 跑 3 个模拟日冒烟。
3. 4 个 persona 各 30 天；同时派 4 个代理 A 各跑 1 次会话（Sonnet 子代理，可并行）。
4. 创始人汇总，写 research 报告；缺陷进台账。
