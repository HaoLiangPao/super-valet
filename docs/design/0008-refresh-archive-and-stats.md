# 路线图：池子引导、月度刷新与雷达重扫、歇业归档、行为统计

> Hao 2026-09-27 一次提出了五组功能。它们有明确的依赖关系，**不能并排开工**，
> 本文件定义分几步、每步交给谁、每步的验收是什么。

## 1. 问题 / Problem

- **老用户看不到新目录**（OPEN-QUESTIONS Q10）。Hao 已裁决：不自动改池子是对的，
  **但必须有像样的引导**，否则 74 家目录对现有用户等于不存在。
- **数据会过期也会消失**。design/0005 §4.8 定了 30 天 TTL，但至今**没有执行者** ——
  没有任何代码会去刷新。而且餐厅会倒闭：推荐一家已经永久关门的店是最伤信任的错误。
- **删掉就什么都没了**。一家吃过十几次的店倒闭后直接删除，会把用户最有价值的
  历史一起抹掉 —— 而那恰恰是日后做「你最爱的餐厅」统计的原料。
- **行为数据只进不出**。`rolls`/`feedbacks` 从 P0 就在记，至今没有任何一个界面
  把它变成用户看得懂的东西。

## 2. 分步计划 / The steps

依赖关系决定顺序，**每一步都可独立上线**：

| 步 | 内容 | 依赖 | 主责 |
| -- | ---- | ---- | ---- |
| **S1** | 界面语言支持（中/英）收尾 | — | 前端 Sonnet |
| **S2** | 池子引导（Q10） | — | 前端 Sonnet |
| **S3** | 可用性与归档的数据模型（ADR-0009） | — | CTO Opus |
| **S4** | 刷新引擎 + 抓取台账扩展 | S3 | CTO Opus |
| **S5** | 雷达重扫界面 + 刷新报告 | S4 | 前端 Sonnet |
| **S6** | 归档列表界面 | S3 | 前端 Sonnet |
| **S7** | 行为统计页 | S3（归档让统计完整） | 前端 Sonnet |

**S1 排第一是有原因的**：i18n 先把 `t()` 装好，之后 S2–S7 的新文案从第一行起
就是双语的；反过来先做功能再补翻译，等于把同一批文案改两遍。

## 3. 各步设计 / Per-step design

### S1 界面语言（详见 design/0007）

中文字典已完成 242 条。剩下：英文字典、`LocaleProvider`/`useT()`、
字符串抽取、设置页切换、测试。

### S2 池子引导

摇一摇页在**池子 < 20 家**时，在牌堆下方显示一条不打断主流程的提示：
「你的池子只有 N 家 —— 加个套餐，或者自己找几家」，两个按钮去 `/packages` 与 `/explore`。
池子页空态同理。**不弹窗、不阻断**：用户想直接摇就能直接摇。

### S3 可用性与归档（数据模型，见 ADR-0009）

- 餐厅增加可用性状态：`operational` / `closed_temporarily` / `closed_permanently`，
  来源是 Places 的 `businessStatus`（已实测可用）。
- 用户侧增加**归档集合**：归档的店**不参与摇一摇**，但历史、后验、统计全部保留，
  可在归档列表里查看，也可以一键恢复。
- 归档 ≠ 移除。移除是从 selection 拿掉；归档是「它还在我的世界里，只是不能去了」。

### S4 刷新引擎

**两种触发，同一条流水线**：

```
触发（自动：有条目超 30 天 / 手动：用户点重扫）
  ↓
① 刷新已有：对过期条目重新拉 Places Details
     → 事实变了就更新（评分/价位/营业时间/businessStatus）
     → businessStatus 非 OPERATIONAL 的进「待处理」清单
  ↓
② 发现新店（仅手动重扫）：按当前位置 + 半径，用目录里已有的菜系做类目搜索
     → 过滤掉已在目录/池子里的
     → 分类 → 作为「新发现」候选呈现，**不自动入池**
  ↓
③ 产出一份刷新报告（RefreshReport）
```

**自动刷新的节制**（成本与体验）：每天最多触发一次；一次最多刷新 20 家；
只在用户打开应用时后台进行，不做定时任务（没有流量之前定时任务是自找运维）。

### S5 雷达界面与刷新报告

- 点「重新扫描」→ 雷达动画（同心圆 + 扫描线，复用 `fx-*` 体系，
  `prefers-reduced-motion` 下退化成进度文字）。
- 结束后给一份**人话报告**：
  ```
  自动刷新 · 2026-10-27 18:30
  更新了 12 家   · 海底捞评分 4.8→4.7、良心冰室营业时间变了 …
  新发现 3 家    · [查看] [全部加入池子]
  需要你确认 1 家 · 老王川菜显示「永久停业」 → [归档] [移除] [先留着]
  ```
- 报告落库（`refresh_reports`），历史可回看 —— Hao 明确要求区分
  **自动触发还是手动触发**、**更新了什么**、**新增了什么**。

### S6 归档列表

设置页或池子页入口 → 归档列表：店名、归档原因（永久停业/临时停业/用户手动）、
归档时间、历史吃过几次。操作：恢复到池子 / 彻底删除。

### S7 行为统计

基于既有 `rolls` / `feedbacks`：

- 「上周你探索了 N 家新店」（首次出现的 placeId 计数）
- 「你最爱的餐厅」（吃过次数 × 好评率，**含已归档的** —— 这正是归档的意义）
- 「你最爱的菜系」（类别层后验 α/(α+β) 排序）
- 「你最常拒绝的理由」（skip_reason 分布）

⚠️ **诚实边界**：research/0002 早就算过，单用户月度样本约 30 条，
统计量的置信区间极宽。所以统计页的定位是**「有趣的回顾」不是「可信的洞察」**，
文案不许说「数据显示你偏好 X」，只说「你去过 N 次 X」这种可直接数出来的事实。

## 4. 风险与未决问题

- **Risk:** 重扫发现新店会烧 Places 配额。**缓解:** 手动重扫每天限 1 次、
  每次最多 8 个类目查询；自动刷新只碰已有条目不做发现。
- **Risk:** 永久停业判断错误（Google 数据滞后）导致误归档。
  **缓解:** **永不自动归档**，一律问用户；提供「先留着」选项。
- **Open:** 归档的店要不要参与「你最爱的餐厅」统计？本设计说要（否则十年老店倒闭后
  统计里凭空消失）。Hao 若不同意再改。
