# S4/S5：刷新引擎、雷达重扫、附近列表与驾车时间估算

> design/0008 路线图的第四、五步。Hao 2026-09-28 追加了两条：
> 雷达可否做成地图（要求内部讨论后给建议），以及**必须**提示大概要开多久车。

## 1. 问题 / Problem

- **30 天 TTL 至今没有执行者**：design/0005 §4.8 定了规矩，但没有任何代码
  会去刷新。74 家目录的营业时间、评分、价位自抓取之后从未更新过。
- **ADR-0009 的语义还悬着**：可用性字段进了 schema，但没有东西去填它 ——
  目前全部按 `OPERATIONAL` 处理，等于「我们不知道，也不承认不知道」。
- **新店进不来**：目录是一次性生成的静态文件，Markham 新开的店永远不会出现。
- **距离是个裸数字**：「5.3 km」对开车的人没有意义，他要知道的是「要开多久」。

## 2. 目标与非目标 / Goals & Non-goals

**Goals**

- [ ] **手动重扫**：用户点一下，刷新已有 + 发现新店，全程有雷达式反馈。
- [ ] **自动刷新**：打开应用时若有条目超 30 天，后台静默刷新（有节制）。
- [ ] **刷新报告**：区分自动/手动触发，说清**更新了什么、新增了什么、
      哪些需要你确认**，可回看。
- [ ] **附近列表**：按用户输入的距离列出范围内的餐厅（这是 Hao 的最低要求，
      也是这个页面的主体内容）。
- [ ] **驾车时间估算**：每家店标「开车约 N 分钟」，并**如实标注是估算**。

**Non-goals（本轮明确不做）**

- **真实地图**（见 §4.1 的讨论与结论）。
- Distance Matrix API 的精确行车时间（按元素计费，见 §4.4）。
- 定时任务 / Cron（没有流量之前是自找运维，design/0008 §3 已定）。
- 自动归档（ADR-0009：永不自动归档）。

## 3. 成功长什么样 / Success criteria

- 点「重新扫描」→ 看得见在扫 → 结束给一份人话报告，读得懂哪几家变了。
- 目录里确实有店的事实被更新（评分/营业时间/`businessStatus`）。
- 半径内列表与摇一摇的候选池**完全一致**（同一个 `localizedPool()`，
  不许两套逻辑 —— 这正是上一轮事故的教训）。
- 每家店都有「开车约 N 分钟」，且文案不谎称精确。

## 4. 方案 / Proposed design

### 4.1 雷达要不要做成地图 —— 内部讨论与结论

| 方案 | 代价 | 结论 |
| ---- | ---- | ---- |
| Google Maps JS API | 新 key + 新计费 SKU、~200KB+ JS、UI 工作量最大 | ❌ |
| Static Maps API（带标记的图片） | 轻，但仍是新 SKU，且不可交互 | 🟡 备选 |
| **SVG 雷达图**（同心距离环 + 方位角打点） | 零新 API、零新依赖、零新成本，可交互 | ✅ **采纳** |

**决定性论据：真地图的用途是导航，而导航我们已经交给 Google Maps 了**
（锁定页的「在 Google Maps 打开」）。在应用里复刻一个地图，是在跟 Google Maps
竞争一件我们不需要赢的事，还会打破「月成本约 $0」这条线。

而雷达要承担的是另外两件事：**扫描时的反馈**（「我们正在你周围找」）
与**池子的空间感**（「我的店都集中在西边」）。SVG 雷达图两件都够用，
同心圆还正好复用摇一摇按钮已有的视觉语言。

**诚实的弱点**：没有街道底图，圆点的方位会显得抽象。缓解：环上标公里数、
正上方标「北」、点圆点出餐厅卡。**列表才是主体**，雷达是列表上方的可视化。

### 4.2 刷新流水线（两种触发，同一条路）

```
触发
 ├ 自动：打开应用时有条目超 30 天（每天至多一次，单次至多 20 家）
 └ 手动：用户点「重新扫描」
      ↓
① 刷新已有：对过期条目重拉 Places Details
     → 记下每个变化的字段（RestaurantDiff）
     → businessStatus ≠ OPERATIONAL 的进「需要你确认」
      ↓
② 发现新店（**仅手动**）：按当前位置 + 半径做类目搜索
     → 滤掉已在目录/池子/归档里的 → 分类 → 作为候选呈现
     → **不自动入池**，用户勾选后才加
      ↓
③ 产出 RefreshReport 并落库
```

**节制条款**（成本护栏，沿用 `refresh-types.ts` 已定义的常量）：
`REFRESH_BATCH_LIMIT = 20`、`AUTO_REFRESH_MIN_INTERVAL_MS = 1 天`；
手动重扫的类目查询**每次至多 8 个**；自动刷新**只碰已有条目，不做发现**。

### 4.3 刷新报告

```
手动重扫 · 2026-10-28 18:30 · 用时 12 秒
更新了 12 家   · 海底捞 ★4.8→4.7 · 良心冰室 营业时间变了 · …
新发现 3 家    · [看看] [全部加入池子]
需要你确认 1 家 · 廿一筷子 显示「永久停业」 → [归档] [移出池子] [先留着]
没有变化 8 家
失败 1 家      · 网络问题，下次再试
```

`RefreshFailure` 必须显示 —— 失败悄悄消失的话，「更新了 12 家」就是假的。

### 4.4 驾车时间估算

design/0002 §6.5 早就指出直线距离在 GTA 会系统性低估（401/DVP 堵车），
精确做法是 Distance Matrix API，但那是**按元素计费**的，而这个数字出现在
列表的每一行 —— 调不起，也不值得调。

所以用启发式，并且**在文案里承认它是估算**：

```ts
const DETOUR = 1.3;          // 网格城市的绕路系数（直线 → 道路）
const SPEED_KMH = 35;        // Markham 主干道含红灯的平均速度
const PARKING_MIN = 3;       // 找车位与走进门
// 驾车分钟 = km × DETOUR / SPEED × 60 + PARKING ≈ km × 2.2 + 3
// < 1.2 km 改显示步行：km × 12（5 km/h）
```

文案：「开车约 12 分钟」+ 一处小字「按直线距离估算」。
**不许写成「12 分钟」这种确定口吻。**

### 4.5 附近列表（Hao 的最低要求，本页主体）

- 半径输入沿用 design/0006 的四档，另加一个自定义输入（1–50 km）。
- 列表数据源**必须**是 `localizedPool()` —— 与摇一摇同一个函数。
  两套逻辑就是上一轮事故的复刻。
- 每行：菜系点 · 店名 · 距离 · **开车约 N 分钟** · 营业状态徽标。

## 5. 备选方案 / Alternatives considered

| 方案 | 优点 | 缺点 | 为什么没选 |
| ---- | ---- | ---- | ---------- |
| 真地图（见 §4.1） | 直观 | 新计费 SKU + 与 Google Maps 重复 | ❌ |
| Distance Matrix 算真实车程 | 准 | 每行一个计费元素 | ❌ 估算够用 |
| Vercel Cron 定时刷新 | 不依赖用户打开 | 无流量时的纯运维负担 | 推迟 |
| 自动把新发现的店入池 | 省一步 | 替用户做主，违反 ADR-0008 | ❌ |

## 6. 风险与未决问题 / Risks & open questions

- **Risk:** 手动重扫烧 Places 配额。**缓解:** 每天 1 次、类目查询 ≤ 8、
  发现结果先去重再 Details。
- **Risk:** 驾车估算与实际差距大，用户被误导。**缓解:** 文案明确是估算；
  如果试玩反馈说偏差大，再考虑对**锁定的那一家**单独调一次 Distance Matrix
  （一天一次、一个元素，成本可忽略）。
- **Open:** 雷达上要不要显示不在池子里的「新发现」？倾向要，用不同颜色，
  这正是「发现」的意思。

## 7. 落地计划 / Rollout
