# 界面语言支持：默认简体中文，支持英文

> Hao 2026-09-26 要求：默认简体中文，同时支持英文。

## 1. 问题 / Problem

全部界面文案是硬编码的中文，散落在十几个组件里。试玩用户里有不读中文的人，
现在等于用不了。同时服务端的错误消息也是中文硬编码，客户端没法本地化。

## 2. 目标与非目标 / Goals & Non-goals

**Goals**

- [ ] 全部界面文案走字典，支持 `zh`（简体，默认）与 `en`。
- [ ] 语言可切换并记住选择；未选过时默认 `zh`（**不跟随浏览器语言** —— 见 §5）。
- [ ] 服务端错误改为「错误码 + 兜底中文」，由客户端按当前语言渲染。
- [ ] 餐厅名、地址、菜品名等**数据**不翻译（它们本来就是专名）。

**Non-goals**

- 繁体中文、其它语种（字典结构留好扩展位即可）。
- 让 LLM 按界面语言输出（分类 `reason` 仍是中文，属数据不属界面；
  英文界面下直接显示，不做机器翻译 —— 见 §6 未决问题）。

## 3. 成功长什么样 / Success criteria

- 切到英文，四个页面 + 设置 + 所有报错提示无一处残留中文界面文案。
- 刷新后语言选择还在。
- 切换语言不丢任何状态（不重新登录、不清池子）。

## 4. 方案 / Proposed design

不引第三方 i18n 库。应用只有五个页面、全是 client component，
`next-intl` 这类方案带来的路由分段、服务端消息加载在这里都是净负担。

```
src/lib/i18n/
  messages.zh.ts   字典（真理源，key 由它定义类型）
  messages.en.ts   必须实现 zh 的全部 key，缺一个 TS 就报错
  index.ts         LocaleProvider / useT() / 语言持久化
```

- `type MessageKey = keyof typeof zh`，英文字典声明成 `Record<MessageKey, string>`
  —— **漏翻一句会在编译期挂掉**，不会等到用户看见。
- 取值 `t('pool.remove.confirm', { name })`，简单占位符替换，不引模板引擎。
- 语言存 localStorage，**与身份无关**（换账号不该换语言）。
- 服务端：`ApiError` 增加 `code` 字段（如 `places.not_found`），
  客户端优先用 code 查字典，查不到才退回服务端的中文 `message`。

## 5. 备选方案 / Alternatives considered

| 方案 | 优点 | 缺点 | 为什么没选 |
| ---- | ---- | ---- | ---------- |
| 自建字典（本方案） | 零依赖、类型安全、漏翻编译期暴露 | 没有复数/日期本地化等高级能力 | 现在不需要那些 |
| next-intl / react-intl | 功能全 | 路由分段与服务端加载对纯客户端应用是负担 | 过度 |
| 跟随 `navigator.language` | 看起来贴心 | Hao 明确「默认简体中文」；GTA 用户浏览器多为 en-CA，会把中文用户默认到英文 | ❌ 违背需求 |

## 6. 风险与未决问题 / Risks & open questions

- **Risk:** 字典与界面漂移。**缓解:** 英文字典用 `Record<MessageKey, string>` 约束，
  漏 key 编译不过。
- **Open:** 英文界面下，LLM 生成的分类 `reason`（如「店名有川菜特色」）仍是中文。
  要不要让分类器按界面语言产出？本轮不做：那会让同一家店在两种语言下存两份数据。
  等有英文试玩用户反馈再定。

## 7. 落地计划 / Rollout

作为 Unit B，**排在 UI 定稿之后**（design/0006 的界面改完再抽字符串），
否则会翻译一批马上要改的文案。
