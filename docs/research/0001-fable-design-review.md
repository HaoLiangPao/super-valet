# Fable 设计评审：design/0001 + design/0002 + 种子数据

> TL;DR：两份文档的产品判断和工程品味都在线，Bandit 建模方向正确。
> 但**最可能让项目失败的不是技术栈，是数据体制** —— 整条 V1→V3 算法路线
> 建立在一个不存在的样本量上。以下按严重程度排序。

## 1. 数据体制：先把样本预算算清楚 🔴

把乐观情形摆出来：每天 1 次决策、反馈回收率按企划书自己的目标 60%
（现实早期更可能 30–50%），六个月净得 **60–90 个有效样本**，摊到
15–30 家店，**每家店每月 1–2 条反馈**。

这意味着：

- **单店级 Thompson Sampling 不会收敛。** 想区分「0.70 的店」和「0.85 的店」，
  Beta 后验标准差要压到 ~0.05，即每家店需要 **~60 条反馈** —— 按上述节奏是
  **年级别**的事。V1 的诚实定位是「有原则的随机化」（乐观先验驱动的探索 +
  冷却驱动的多样性），不是「学习你的口味」。这不丢人，随机化本来就是
  这个产品 80% 的价值；但排期和卖点要按这个定位写。
- **算法版本之间的差异统计上不可检测。** 月度约 30 次决策，采纳率的
  95% CI 半宽 ≈ 1.96·√(0.25/30) ≈ **±18–20pp**。V0→V1→V2 谁更好，
  在个位数月份内测不出来。结论：企划书 P2 的数据看板、熵监控应**大幅后移**——
  别给检测不到的信号造仪表盘；`rolls.candidates_snapshot` 留好，
  等两年后有数据了做离线回放。

## 2. 两层 Bandit：schema 现在就加类别层，打分用软乘积 🟡

design/0002 的层次先验（§5.1）方向对。落地建议：

- **现在就进 schema**：`user_cuisine_categories(user_id, category, alpha, beta)`，
  与 `user_restaurants` 平行。类别层 12 个臂，每臂每月能摊到 2–5 个样本，
  是唯一在人类时间尺度内真正能「学到东西」的层。
- **但不要做硬两阶段采样**（先抽菜系、再在菜系内抽店）—— 小池子里
  很多类别只有 1–2 家店，两阶段会放大方差且难调试。用**软乘积**：
  `final_i = θ_store_i × θ_category(i)^γ × freshness_i × distanceWeight_i`，
  γ 起步 0.5。单店 θ 长期近似先验，实际驱动力来自类别层 —— 这正好符合第 1 节的样本现实。

## 3. 多样性坍缩的真实形态是几何坍缩 🟡

企划书 §10 担心的「回音室」在这个数据量下不会由算法造成（算法根本
学不到那么快），会由**硬过滤的几何**造成：工作日午餐过滤
`soloFriendly + slotLock + 营业中 + 距离`之后，15 家的池子只剩个位数，
而幸存者的菜系高度相关。熵下降的第一元凶是池子结构，不是 (α,β)。

**唯一真解是把池子扩到 30–40 家**，且按「时段 × 场景」的覆盖去补
（工作日午餐单人友好的缺口最大），这是数据工作不是代码工作。
监控熵、调探索强度都只是在小池子里搅拌。

## 4. 技术栈异议（详见 ADR-0003，此处只给理由）🟡

- **反对 PostGIS**。≤100 家店，Haversine 在应用层一个循环就算完
  （种子文件里已经有 `haversineKm` 了）。PostGIS + geography 类型 + RPC +
  绕开 ORM，是给「全城几万家」准备的架构，在这里是纯负债。
- **iOS 上的 Web Push 是整套方案最大的技术风险**。它要求用户先把 PWA
  加到主屏、权限链路脆弱、iOS 版本敏感，而「20:00 追问反馈」恰恰是
  数据管道的命脉（回收率 <60% 模型就断粮）。建议：**反馈通道用 Telegram bot**
  （一个 webhook，闭环一条消息），PWA 只做「摇一摇」主交互。两者不互斥。
- Drizzle 本身没问题，但推荐算法的手写 SQL 比例会很高，别为了 ORM 纯度绕路。

## 5. 种子数据 bug：`isOpenAt()` 对 `day: null` 的跨零点窗口失效 🔴（已验证）

`data/seed-restaurants-markham.ts` 的 `isOpenAt()`：海底捞
`{ day: null, open: '11:00', close: '26:00' }`，凌晨 1:00 调用返回 `false`，
实际营业到 2:00。原因：`day === null` 恒命中第一个分支，
`close > 1440` 时只检查 `mins >= open`（60 ≥ 660 为假）；而「前一天窗口
延伸到今日凌晨」的补偿分支要求 `win.day !== null`，`day: null` 永远进不去。
周五六的 Number One BBQ 用具体 day 表示所以没事，**只有 day: null 的
跨零点窗口中招**。修法（一行）：

```ts
if (win.day === null || win.day === day) {
  if (close <= 1440) return mins >= open && mins < close;
  return mins >= open || (win.day === null && mins < close - 1440);
}
```

## 6. 创始人追加的一个范围问题：Supper Valet 到底管几餐？🟡

项目叫 **Supper** Valet，repo 定位写的是「今天**晚上**吃什么」，
但企划书的核心场景是 11:30 的午餐推送，指标、距离参数（`d0` 表）
也都按午+晚双场景设计。这不是抠字眼：**午餐决策（时间紧、单人、就近）
和晚餐决策（可凑人、可专程）是两个产品形态**，样本预算（第 1 节）
砍半还是集中，取决于这个选择。我的立场：V0 只做晚餐，把每天唯一的
样本花在同一个分布上；午餐等晚餐闭环跑顺再开。待 Hao 裁决（OPEN-QUESTIONS Q7）。

## 7. 下周该写的第一个文件：`sim.py` ✅

15 家种子店 + 真实营业时间/距离，模拟 180 天决策流（合成用户偏好 +
30–50% 反馈回收），对比 V0 / V1 / 软乘积两层方案的采纳率与菜系熵。
一个下午的工作量，能用数据直接关掉 OPEN-QUESTIONS 里一半的问题
（Q1 两层结构、Q5 冷启动方案、部分 Q6），比任何继续写文档都值。
