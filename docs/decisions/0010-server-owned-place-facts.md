# ADR-0010: 餐厅事实归服务端，按店全局刷新一次；用户只负责发现与报告关门

> 状态说明：Hao 2026-10-01 在对话中同意了下面的四点（台账 Q16）。按授权规则，
> 创始人不自行把决策转 `accepted`，等 Hao 复核本文后转。

## 背景 / Context

现在的刷新（design/0009 §4.2）跑在**客户端**：每个用户打开应用时，`maybeAutoRefresh()`
把**他自己池子里**过期的店拉一遍 Places Details，`fetchedAt` 记在**他自己的**池子条目上。

问题在于同一家店是多个用户共享的。10 个用户的池子里都有「名粤軒」，它一个月就被抓 10 次。
Places 的成本因此跟着「用户数 × 店数」涨，而不是「店数」。按 Google 2025 年 3 月起的计价，
Enterprise 档每月约 1,000 次免费，一个池子按 50 家算，**约 20 个活跃用户就会用完** ——
正好是 pilot 的规模。

2026-10-01 已经先把刷新的字段配置降了一档（design/0009 §6.1，Q16①），
但那只是把单价降下来，没有改变「乘以用户数」这件事。

Places (New) 不返回「最后修改时间」，也没有 etag，没有便宜的办法判断「这家店变了没有」，
只能定期去拉。所以能省钱的唯一办法是**一家店只拉一次，所有人共用结果**。

## 决策 / Decision

**我们决定把餐厅的事实字段（坐标、营业时间、评分、价位、营业状态）改为按 `placeId`
全局存一份、只由服务端写入，由服务端定时任务按店刷新；用户触发的操作只负责「发现新店」
和「报告关门」，不再刷新已有店。**

具体四点（Hao 2026-10-01 同意）：

1. **共享事实表**：目录店和用户导入的店，事实都进同一张按 `placeId` 唯一的表，
   只有服务端（service role）能写。用户私有的只剩：池子选择、笔记原文、菜品、
   对分类的手改、归档。导入的店若没有这一步，定时任务根本不知道它们存在。
2. **服务端定时刷新，两档频率，都按店计**：
   - 每周查一次 `businessStatus`（Pro 档）—— 发现关门主要靠它；
   - 每月拉一次完整事实（Enterprise 档，即 Q16① 的窄 mask）。
   只刷新**至少在一个用户池子里**的店；Vercel Cron 每天跑一次，每次处理最旧的 N 家。
3. **发现结果共享缓存**：按「区域 × 类目词」缓存 7 天。同一区域一周内的重扫直接读缓存，
   不再调用 Places。手动「重新扫描」从此**只做发现**，不再刷新已有店。
4. **用户的「关门」报告是信号，不是刷新**：摇到的店去了发现关门，用户可以在反馈里说
   「到了发现关门」；归档列表里也有「查一下它重开没有」（Q13）。这会触发服务端对
   **这一家**的状态检查，结果写进共享表，7 天内的重复请求直接读缓存。
   用户报告与 Places 不一致时（用户说关了、Places 说营业中），**以用户自己的判断
   约束他自己的池子**（引导他归档），不改共享表里 Places 给的事实 ——
   一个人的报告不能替所有人下结论。

## 理由 / Rationale

- 成本从「用户数 × 店数」变成「店数」。按 100 家在池子里的店算，每月约
  400 次 Pro + 100 次 Enterprise，都在免费额度内，**用户再多也不变**。
- 事实本来就不属于用户：营业时间是 Google 的数据，不是用户的偏好。
  每人一份只会让同一家店在不同用户那里显示不同的营业时间。
- 用户在现场的观察比 Places 更快（Places 的停业状态常常滞后几周），
  把它作为触发检查的信号，既利用了这个信息，又不让刷新频率被用户行为左右。

## 备选 / Options considered

| 选项 | 优点 | 缺点 | 结论 |
| ---- | ---- | ---- | ---- |
| 维持现状（客户端、每人一份） | 不用改 | 成本随用户数线性涨，约 20 人用完免费额度 | 否 |
| 只共享目录店，导入店仍每人一份 | 迁移小 | 导入店才是长尾，仍按人数重复抓；两套刷新逻辑并存 | 否 |
| 用便宜的「冒烟测试」判断要不要拉完整详情 | 理论上省 | Places 没有修改时间；状态字段抓不到营业时间的变化 | 否，仅作为每周状态检查 |
| **服务端按店刷新 + 共享事实表（本决策）** | 成本只跟店数有关；数据一致 | 要改数据归属、加定时任务和服务端写权限 | **采纳** |

## 后果 / Consequences

**得到**
- Places 成本与用户数脱钩。
- 所有用户看到的同一家店事实一致。
- 停业能在一周内发现（现在最长要等一个月，且只有打开应用的用户才会触发）。

**付出 / 接受的代价**
- **数据归属变更**：需要新迁移（共享事实表 + RLS：所有登录用户可读、只有 service role 可写），
  并把现有用户池子里导入店的事实迁过去。这是一次**改写已有数据**的迁移，
  按授权规则上线前要 Hao 当次批准。
- 服务端需要 service role 凭证和定时任务；Vercel Hobby 套餐的 cron 每天最多一次，够用但没有余量。
- 用户点「重新扫描」后不再看到「更新了 N 家」，刷新报告的形态要改（design/0009 §4.3）。
- 客户端的 `maybeAutoRefresh()` 及其接线测试（`auto-refresh-wiring.test.ts`）将被移除，
  由服务端定时任务的测试取代。

**什么情况下应该重新考虑这个决定**
- 定时任务的处理量超出 Hobby 套餐的 cron 限制（店数涨到每天处理不完）。
- 用户大量手改事实字段（例如自己修正营业时间）—— 那时事实就不再纯属 Google，
  需要「共享事实 + 用户覆盖」的两层结构。
- Places 推出变更通知或修改时间字段，定时拉取就不再必要。

## 落地顺序

排在 S6（归档列表）之后、pilot 扩大之前：
1. 迁移：共享事实表 + RLS；把目录店和已导入店的事实迁入。
2. 服务端：定时任务路由（周状态 / 月事实）+ 单店状态检查路由（带 7 天缓存）。
3. 客户端：移除自动刷新；重扫只做发现；反馈里加「到了发现关门」。
4. 发现缓存（区域 × 类目词，7 天）。
