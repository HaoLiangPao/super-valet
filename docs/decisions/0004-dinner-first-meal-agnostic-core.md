# ADR-0004: V1 范围只做晚餐，推荐内核对餐次无感知

## 背景 / Context

项目定位（Supper Valet，「今天晚上吃什么」）与 design/0001 的核心场景
（11:30 午餐推送）存在范围分歧（原 OPEN-QUESTIONS Q7）。模拟已排除数据
论据：午+晚共用无上下文模型对晚餐质量的代价 ≈ 0.6pp，噪声级
（research/0002 发现 5），因此这是纯产品范围判断。Hao 于 2026-09-17 拍板。

## 决策 / Decision

**我们决定 V1 只做晚餐一个决策闭环；但推荐内核（打分、后验、冷却、
池过滤）以 meal 为参数设计，对餐次无感知。**

## 理由 / Rationale

Hao 的判断：午餐与晚餐的差别只在「开着的餐厅不同、地理锚点可能不同、
用户群不同」，底层逻辑应是同一套。因此午餐日后是**新增一份 meal 配置**
（候选过滤器 + 锚点 + 距离参数 d0），不是新系统。工程上先把一个闭环
跑顺，交付面减半。

## 备选 / Options considered

| 选项 | 优点 | 缺点 | 结论 |
| ---- | ---- | ---- | ---- |
| 写死晚餐 | 最快 | 加午餐时要翻修内核 | ❌ |
| 一次做两餐 | 场景全 | V1 交付面翻倍，习惯培养分散 | ❌ |
| 晚餐先行 + 内核无感知 | 快且不留债 | 需要一点参数化设计 | ✅ |

## 后果 / Consequences

**得到**
- V1 的推送、反馈、指标都只有一个时段，闭环简单。
- 池子扩充（research/0001 §3 的 30–40 家目标）优先补晚餐场景覆盖。

**付出 / 接受的代价**
- 午餐使用习惯的培养推迟。

**什么情况下应该重新考虑这个决定**
- 晚餐闭环稳定使用 ≥ 4 周后，评估开启午餐配置。
