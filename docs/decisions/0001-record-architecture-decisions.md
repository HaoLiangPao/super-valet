# ADR-0001: 用 ADR 记录架构决策

## 背景 / Context

Supper Valet 会经历大量选型决策：推荐算法怎么做、数据存哪、前端用什么、要不要接外部菜谱 API。这些决策的**理由**比决策本身更容易丢失 —— 三个月后看到一段代码，谁也想不起当初为什么这么写，于是要么不敢改，要么改错。

## 决策 / Decision

**每一个有长期影响、且难以廉价撤销的技术决策，都在 `docs/decisions/` 下写一篇 ADR。**

- 文件名：`NNNN-短横线标题.md`，编号单调递增，永不复用
- ADR 一旦 `accepted` 就不再修改内容；要改变决策就写新的一篇，把旧的标为 `superseded` 并填 `superseded_by`
- 判断标准：如果六个月后有人问「为什么是这样？」而答案不显然 —— 写 ADR

不需要 ADR 的：库版本升级、代码风格、能在一个下午撤销的事。

## 理由 / Rationale

ADR 的成本很低（十五分钟），收益出现在最需要的时刻 —— 有人想推翻某个设计的时候。它把「争论」变成「可追溯的记录」，也让 AI 协作者（Claude / Fable）能读懂这个项目的历史约束，而不是每次都从零猜。

## 备选 / Options considered

| 选项 | 优点 | 缺点 | 结论 |
| ---- | ---- | ---- | ---- |
| ADR（Markdown in repo） | 和代码同源、随 PR 评审、diff 可读 | 需要自律 | ✅ 选中 |
| Notion / 飞书文档 | 好写好搜 | 和代码脱节，容易过期，AI 读不到 | ❌ |
| 只在 PR 描述里写 | 零成本 | 无法索引，PR 一多就找不到 | ❌ |
| 不记录 | 最省事 | 决策理由三个月内蒸发 | ❌ |

## 后果 / Consequences

**得到**
- 每个决策都有一个可引用的编号（`ADR-0007`），design doc 和代码注释都能链过去
- 新人（和 AI）读 `docs/decisions/` 就能补齐上下文

**付出 / 接受的代价**
- 每个大决策多花约 15 分钟
- 需要 CI 强制索引更新，否则文档会漂

**什么情况下应该重新考虑这个决定**
- 如果项目最终只有一个人、且生命周期短于三个月，这套流程可能过重
