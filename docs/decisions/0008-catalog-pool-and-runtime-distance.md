# ADR-0008: 目录与池子分离；距离改为运行时计算

> status: **proposed** —— 改的是核心数据模型，请 Hao 复核后转 accepted。

## 背景 / Context

Hao 2026-09-26 要求三件事：池子可增可删、支持「精选套餐」（如「评分高的中餐」
「性价比西餐」）、按 GPS 位置和半径筛选餐厅。三件事指向同一个前提。

今天的模型里**「我们知道的餐厅」和「你池子里的餐厅」是同一个东西**：
`SEED_RESTAURANTS` 那 15 家既是全部库存，也是每个人的池子。于是：

- 要做套餐，就得有一个比池子大的库存可供挑选 —— 现在没有。
- 要把新抓的 40 家店放进生产，会直接塞进**每个人**的池子，等于替用户做主。
- `distanceKm` 是**导入时**按 Downtown Markham 算死写进记录的。用户在别处
  打开应用，看到的距离是错的，按半径筛选更无从谈起。

## 决策 / Decision

**1. 目录（catalog）与池子（pool）分离。**

- **目录** = 我们维护的全部餐厅（种子 15 家 + 本轮批量导入的若干家 + 用户自己导入的）。
- **池子** = 用户**显式选中**的子集，存一份 `placeId` 列表。
- **套餐** = 目录的命名子集，我们自己维护（`src/data/packages.ts`）。
  「加入套餐」= 把该套餐的 placeId 并进池子，之后用户可以单独删掉其中任何一家。

**向后兼容**：老用户没有显式选择记录，首次加载时把池子默认成原来的 15 家种子，
行为与今天逐字节一致，不会有人一觉醒来发现池子变了。

**2. 距离不再是餐厅的固有属性，而是「餐厅 × 当前位置」的函数。**

记录里保留 `lat/lng`（事实）与导入时算的 `distanceKm`（仅作兜底展示），
但**推荐与筛选一律用运行时重算的距离**：

```
poolRestaurants(location, radiusKm) →
  目录 ∩ 池子 → 按 location 重算 distanceKm/bucket → 按 radiusKm 硬过滤
```

**引擎一行都不改。** 这是刻意的：`eligible()`/`scoring` 只认传进去的
`Restaurant[]`，把「按当前位置本地化并筛选过的餐厅列表」喂给它即可。
71 个既有测试因此全部继续有效。

**3. 位置采用双轨制（落实 design/0002 §6.1，关掉 OPEN-QUESTIONS Q2）。**

`anchor`（用户设定的家/公司，默认 Downtown Markham）为主，`gps` 为可选。
GPS 只在用户主动开启时请求，缓存 15 分钟，失败沿着
「GPS → 上次成功位置 → 当前锚点 → 默认锚点」降级，**任何一环都不给空列表**。

## 理由 / Rationale

- 把「库存」和「我的选择」分开是这三个功能共同的前提，分开一次三件事都成立。
- 距离运行时算是唯一诚实的做法：位置本来就是会变的上下文，不是餐厅的属性。
- 不动引擎是最省的实现路径，也保住了既有测试的全部价值。

## 备选 / Options considered

| 选项 | 优点 | 缺点 | 结论 |
| ---- | ---- | ---- | ---- |
| 目录/池子分离（本决策） | 三个需求一次到位；用户掌控自己的池子 | 多一层选择状态要存与迁移 | ✅ |
| 新店直接塞进所有人池子 | 零改动 | 替用户做主；池子迅速失控 | ❌ |
| 距离仍然写死，按锚点筛选 | 不用碰 GPS | 用户不在锚点时距离全是错的 | ❌ |
| 在 `eligible()` 里加半径参数 | 看起来更「内聚」 | 要改引擎与全部调用点，危及 71 个测试 | ❌ 喂数据更省 |

## 后果 / Consequences

**得到**
- 池子可增可删；套餐可以一键加入；半径筛选成立；批量导入不再打扰任何人。
- 目录可以放心长大（本轮起到 50+ 家），这是 research/0001 §3「几何坍缩」的解药。

**付出 / 接受的代价**
- 多一份「池子选择」状态要在两个后端存、要为老用户做默认迁移。
- 每次摇一摇多一遍距离重算 —— 50 家店的 Haversine 是微秒级，无所谓。
- 目录数据由我们维护，意味着我们要对它的时效负责（30 天 TTL，见 design/0005 §4.8）。

**什么情况下应该重新考虑这个决定**
- 目录涨到几千家：那时需要召回层，不能再全量打分（design/0001 假设 A2 会失效）。
- 用户开始期望「附近实时发现」而不是「维护自己的池子」——那是另一个产品。
