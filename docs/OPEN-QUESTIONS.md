## 🟡 影响开发顺序的

### Q4 推送/反馈通道：Web Push、Telegram bot，还是「无推送、下次打开补问」？

先拆干净三个概念（2026-09-17，源自 Hao 的追问「简单网页行不行」）：

1. **主交互（拉）** —— 用户主动打开、摇一摇。一个普通移动端网页就够，
   PWA 的「安装到主屏」只是入口优化 + iOS 上解锁 Web Push 的前置条件。
   **这一层没有争议，简单网页即可。**
2. **推送（推）** —— 17:00 主动找到用户说「今晚吃这家」。网页自己做不到；
   iOS 上必须 PWA 安装 + iOS 16.4+ + 授权，链路脆弱。
3. **反馈（收）** —— 20:00 追问「怎么样」。这是数据管道的命脉。

三个候选方案（只争 2 和 3）：

| 方案 | 机制 | 代价 |
| ---- | ---- | ---- |
| A. iOS Web Push | PWA 安装后系统推送 | 链路脆弱、静默失败、design/0001 原案 |
| B. Telegram bot | webhook 推送 + 单击反馈 | 多一个 App 的心智成本 |
| C. 无推送 | 下次打开网页时补问「昨天那家怎么样？」 | 回收率↓、延迟、回忆偏差 |

- 🅕 原立场：主交互用简单网页；反馈通道押 B。
- **sim 修正了我的立场**（research/0002 发现 4）：回收率 30% vs 90% 在 180 天
  尺度上对所有指标无影响 —— 学习主要靠摇的当场 skip 信号，不靠吃后评分。
  「反馈管道断粮」论据作废；推送剩下的价值是**提醒用户今天来用**（sim 未建模）。
- 🅕 修正后立场：**V1 用方案 C（简单网页 + 下次打开补问）起步**，
  推送通道（A vs B）等真实使用数据暴露「忘了用」的频率后再裁决。

### Q5 冷启动：层次先验（κ 继承）够不够？要不要 Bradley-Terry 式配对比较问卷？

- design/0002 §5.1 的 κ=0.25 继承是当前方案。
- 🅕 先验继承够了；配对问卷的信息量撑不起交互成本。
- **sim 间接支持关掉**（research/0002 §六）：乐观先验 + 类别层已够；
  κ 继承的具体值留到真有新店加入时再校准。

### Q6 「摇一摇」是使用门槛还是仪式感？

- design/0001 视其为核心交互；另一派观点：应该到点直接推送结果，零动作。
- 🅕 倾向「推送默认 + 摇一摇兜底」，但承认这是产品品味问题，数据说了不算。

## 🟢 本轮新增（2026-09-26，Round 5 的遗留）

### Q8 `exportAll()` 不含池子选择、位置偏好与导入记录

「导出全部数据」实际导不全：它住在 `src/lib/engine/store.ts`，而池子选择
（selection）、位置偏好、导入的餐厅都是后加的。导出再导入会丢掉用户辛苦挑的池子。
- 🅕 建议把 `exportAll` 从 engine 目录挪到 `src/lib/store/`，它本来就不是引擎的事。
- 优先级：中 —— 现在没人真的在用导出恢复数据，但「导出」这个承诺是假的，不该拖太久。

### Q9 导入的餐厅没有彻底删除的入口

池子页的「移除」只调 `removeFromSelection`，不动导入记录（餐厅事实/菜品/笔记原文）。
确认弹窗明说了「历史和口味数据都会留着」，所以**不算撒谎**，但意味着
用户导错一家店之后，那份数据永远留在存储里，没有任何界面能清掉。
- 🅕 倾向在确认弹窗里加第二个选项「连同导入的资料一起删掉」，
  调 `removeImported`；默认仍是保守的「只移出池子」。
- 优先级：低 —— 数据量小、不影响推荐，但试玩用户可能会问。

### Q10 老用户的池子仍是 15 家，目录涨到 74 家不会自动进任何人的池子

这是 ADR-0008 刻意要的（不替用户做主），但代价是
research/0001 §3 的「几何坍缩」**只有在用户主动加套餐之后才真的解决**。
- 🅕 这是产品引导问题不是数据层问题：建议池子 < 20 家时在摇一摇页顶部
  提示一次「你的池子只有 N 家，试试精选套餐」。
- 优先级：高 —— 不解决的话这一轮的 74 家目录对老用户等于不存在。

### Q11 「发现新店」的半径不该跟着池子半径一起「不限」（2026-09-28 实测发现）

池子半径默认 `ALL`（design/0006 §4.3 刻意选的：新用户不该因为没设过的筛选看到空池子）。
但 `discoverNearby` 复用了同一个半径，于是手动重扫会**扫遍整个 GTA** ——
实测一次重扫发现 8 家，其中多家在 16–23 km 外。

问题在于两个「不限」语义不同：
- **池子不限** = 「显示我选过的全部」→ 合理。
- **发现不限** = 「去全城找」→ 把 Places 配额烧在引擎几乎不会推荐的店上。
  工作日晚餐 `d0=6`，20 km 的店距离权重 `exp(-20/6)=0.036`，
  2 km 的是 `0.72` —— 相差 20 倍，等于往池子里塞噪音。

- 🅕 建议：发现用**独立上限** `min(池子半径, DISCOVERY_MAX_KM=15)`，
  并在报告里写明「在 15 km 内找到 N 家」。
- 优先级：中 —— 功能可用，但每次重扫都在浪费配额并稀释池子。

### Q12 刷新失败的兜底文案是中文硬编码，英文界面会看到中文（2026-09-28）

`RefreshFailure.message` 在契约里被定义成「中文短句」。端口层出的失败会查字典
本地化，但流水线自己的兜底句（如「这家店没抓到，下次再试」）是硬编码中文，
英文用户会在刷新报告里看到中文。

- 🅕 修法：给 `RefreshFailure` 加 `code`（同 `ApiError` 的做法），
  客户端优先按 code 查字典，message 退为兜底。要动契约，所以没在本轮做。
- 优先级：中 —— 只在刷新失败时可见，但英文用户一旦碰到就很突兀。

### Q13 归档的店不参与刷新，重开了也不会被发现（2026-09-28）

一家「临时停业」被归档后就不再刷新，所以它重新营业我们永远不知道，
只能靠用户自己想起来去归档列表恢复。

- 🅕 倾向：S6 归档列表上给一个「查一下它重开没有」的按钮，按需刷新单家，
  而不是把归档的店塞回自动刷新（那会让每月配额花在用户已经放弃的店上）。
- 优先级：低 —— 等 S6 做归档列表时一并考虑。
